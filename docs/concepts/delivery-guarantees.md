# Delivery guarantees

This page says exactly when the engine hands an email, a LinkedIn action or a post to its provider, when it tries again, and what it records when it cannot tell whether something went out. Every cell of the [table of proofs](#proofs) names the test that keeps it true; `tests/delivery-invariant-doc.test.ts` fails when a test is missing.

## The rule

> **Every outbound action is handed to its provider at most once per attempt, and a new attempt starts only with proof or a decision.** An attempt is the claim of one message row (compare and set on its status and attempt number). The engine starts another attempt on the same row only when (a) the error happened before anything was handed over, (b) it has positive proof the earlier attempt did not arrive, or (c) a person decides with `resolve_unknown`. It never makes more than one automatic extra attempt. When it cannot tell whether a handover arrived, the row becomes `unknown`: nothing is retried until a check or a person settles it. Nothing that might have gone out is ever recorded as `failed`, and nothing is ever sent twice without a record: a second copy that turns out to have gone out anyway is recorded as a duplicate (event, problem, count).

Posts follow the same rule with their own row: a post is claimed from `approved` or `scheduled` to `publishing`, and settled with `manage_posts` action `resolve_unknown`.

The decision in (c) is a person's: `manage_messages` action `resolve_unknown` with outcome `resend` (and `manage_posts` with `republish`) from anyone but a person holding `approve` creates an approval instead. The row stays `unknown` and nothing is queued until a person approves it.

## Words

| Word | Meaning |
| --- | --- |
| Attempt | One claim of a message (`scheduled` to `sending`) or a post (`approved` or `scheduled` to `publishing`). The claim adds one to the attempt number. Every write of the result checks that the claim still holds, so two workers never both hand the same row over, and the answer of an attempt that lost its claim is never recorded as the current one |
| Handover | The moment the provider may have received the action: the SMTP DATA command of an email, the request that sends an invitation, message or comment, the request that publishes a post |
| Before handover | The attempt stopped before anything could reach the provider: a connection that never opened (refused, no DNS answer, or timed out while opening), a call stopped before it was sent (its job had run out of time), missing settings or credentials, a login refused, a refusal or rate limit answered before the action was taken, a local check. Safe to try again on the same row |
| `unknown` | The handover may have happened, but no clear answer came back: a timeout or a dropped connection after the request, a server error (5xx), an answer that cannot be read, a worker that stopped mid-send. Nothing is sent again until a check or a person settles it |
| Proof of non-arrival | Positive evidence that an attempt did not arrive. Email: the mailbox is proven to keep copies of what it sends (the engine found one of its own emails in its Sent folder, `sent_copies_seen_at`) and the copy is still missing after 3 lookups. LinkedIn invitation: the live profile shows no pending invitation and no connection after 3 lookups |
| Duplicate | A second copy that went out: an earlier attempt's answer came late and said it went out, after the engine had sent the row again. Recorded, never silent: see [Duplicates](#duplicates) |
| At least once by design | Actions where a repeat is harmless or the receiver can drop it: see [At least once by design](#at-least-once-by-design). The rule above does not cover them |

## What happens at each boundary

### Campaign emails (B1) and email replies (B2)

Both go through the `email.send` job.

- **Claim:** only a `scheduled` email becomes `sending`, under a lock on its mailbox that checks the daily limit once more.
- **Before handover:** a refused connection, DNS, TLS, a refused login, the send deadline or the job ending before the data, or any 4xx or 5xx answer from the server (also one to the data itself): retried on the same message, or bounced or failed when retrying cannot help. `failed` means the server never took the email.
- **No clear answer:** a timeout or a dropped connection after the data, the 90-second send deadline or the job ending once the data had started, or a worker that stopped mid-send: the email becomes `unknown` (event `message.unknown`).
- **Accepted:** any answer that took the message counts as sent, with or without a queue id. Only an explicit refusal of this recipient means it did not go out. Addresses are compared in lowercase with the domain in its ASCII (punycode) form, so a server that reports the address in another form never turns a delivered email into a failure.
- **Checks:** every 10 minutes `email.reconcile_sends` looks for the Message-ID in the mailbox's Sent folder. Found: `sent`. Missing after 3 lookups: sent again once, with the same Message-ID, only when the mailbox is proven to keep copies; otherwise, and when that second try has no clear answer either, a `send_unknown` problem asks a person. Google and Microsoft mailboxes usually keep copies, but only a copy of one of the engine's own emails proves it; `smtp-relay.gmail.com` never counts. Details: [Mailboxes](../guides/mailboxes.md#sends-with-an-unknown-outcome).
- **Repeated requests:** `reply_to_thread` action `send` (`threads.send_reply`) with the same text in the same thread within 24 hours returns the reply already asked for, with a note, instead of a second one. Text is compared trimmed, with every run of whitespace as one space; a reply that was cancelled, failed or skipped does not count. Calls on the same thread take turns, so two that arrive at the same moment are one reply too: the second finds the reply, the approval or the queued send of the first. A campaign step gets one message per step, also when two workers run the same enrollment.

### LinkedIn invitations (B3)

- **Claim:** only a `scheduled` action becomes `sending`. The job's cancel signal goes with every provider call, so no call outlives its job.
- **Before handover:** a rate limit, a refusal, a restricted or disconnected account, a connection that never opened, a failure while reading the profile before the invitation: retried on the same message, or failed when retrying cannot help. While the LinkedIn provider is paused for the workspace (its key, quota or access refused, with a `provider_down` problem), an action waits instead: it stays `scheduled` and is tried again after the quota wait, else an hour (at least 15 minutes), never failed for it.
- **No clear answer:** a timeout or a dropped connection once the connection was open, a server error (whatever its text says: a 5xx is never read as a rate limit or a restriction), or an answer that cannot be read: `unknown`.
- **Accepted:** an answer without an invitation id counts as sent. A 2xx answer whose body broke off is not proof (something in between can answer 2xx too): `unknown`.
- **Checks:** the person's live profile. A pending invitation or a connection: `sent`. Nothing after 3 lookups: sent again once; when that one is unclear too, a person decides. A resend reads the profile first: when it finds the invitation pending or the person connected after all, the earlier try went out, and the invitation is recorded as `sent`, not skipped.
- **Repeated requests:** a campaign step gets one invitation per step.

### LinkedIn messages (B4)

Campaign steps and replies in a LinkedIn conversation.

- **Claim, before handover, no clear answer:** as for invitations. A message goes out without a lookup when the person's chat or LinkedIn member id is known; otherwise Unipile reads the profile for the member id first, as part of the send, so a timeout or a server error on that read makes the message `unknown` too. A refusal, a rate limit, a paused provider or a connection that never opened counts as before handover.
- **Checks:** a `send_unknown` problem asks a person at once. When the provider can read recent messages, the same text sent by the account in the person's own conversation (the thread's chat, or a chat the person wrote in) confirms it. The same text in another conversation proves nothing. A message is never sent again on its own: missing from the chat list is not taken as proof, since that list can lag.
- **Repeated requests:** one message per campaign step, and the same reply text asked again within 24 hours is the same reply.

### LinkedIn comments (B5)

- **Claim, before handover, no clear answer:** as for invitations (a failure while finding the post to comment on counts as before handover).
- **Checks:** a `send_unknown` problem asks a person to look at the post's comments. A comment is never sent again on its own.
- **Repeated requests:** a campaign step gets one comment per step.

### LinkedIn posts (B6)

Both publishers (`linkedin_official` and Unipile) share this path.

- **Claim:** an `approved` or `scheduled` post becomes `publishing` (`publish_attempt` goes up by one). Two runs never both publish it. Approving publishes at once; a post still `approved` 10 minutes later was left by a run that stopped before its claim (nothing reached LinkedIn), and `content.publish_due` publishes it. Moving the time of such a post (`manage_posts` action `update`) makes it `scheduled` for that time.
- **Before handover:** a refusal, the member's rejected token (the posting account is then marked expired), bad input, missing credentials or an inactive account: `failed`. A rate limit, a connection that never opened or a call stopped before it was sent: `scheduled` again for a later try, 5 tries in all, and `content.publish_due` claims no more posts once its run is out of time. A paused publisher (its app credentials or API key refused or its quota used up, with a `provider_down` problem) is a wait: `scheduled` again for when the pause may end (after the quota wait, else an hour, at least 15 minutes), not counted in the 5 tries and never `failed`; the posting account stays connected. `failed` means nothing reached LinkedIn, so a failed post can be published again.
- **No clear answer:** a timeout or a dropped connection once the connection was open, a server error or an outcome the publisher calls unknown: `unknown` with a `send_unknown` problem. A run that stopped mid-publish is found by `content.publish_due` after 15 minutes and becomes `unknown` too.
- **Accepted:** an answer without a post id (an empty answer, or one in the provider's own format without the id) counts as `published`, with a note that the link is missing. A 2xx page that is not the provider's answer at all (an HTML page from something in between) may never have reached LinkedIn: `unknown`, checked by a person. So is a 2xx answer whose body broke off, unless LinkedIn had already named the post in its headers (`linkedin_official`'s `x-restli-id`): then it is `published` with that id and its link. A server error whose body broke off is read from its status: `unknown`.
- **Settling:** `manage_posts` action `resolve_unknown` (`posts.resolve_unknown`) with outcome `published` (add the `url` when you found it), `republish` (publish it again; it waits for a human approval unless a human with the `approve` scope asks, and needs the `send` scope) or `cancel` (back to draft). A `republish` waiting for approval covers only the try it was asked about: publishing the post again directly cancels it, and approving it after the post was published again changes nothing. `publish`, `schedule`, `update` and `cancel` refuse an `unknown` post and point to `resolve_unknown`. Posts list shows a `note` saying what to do.
- **Repeated requests:** publishing a published post returns it as it is.

## Duplicates

When the answer of an attempt that lost its claim says the action went out, what the engine records depends on the row:

| The row now | What the engine records |
| --- | --- |
| Sent by a newer attempt too | A duplicate: `why.duplicate_attempts` lists both attempts, the event `message.duplicate` fires, a `duplicate_send` problem (normal severity, for a person, one per message) says there is nothing to undo, and the campaign report counts it in `duplicates` |
| A newer attempt is handing it over right now | The row remembers that the earlier attempt went out. If the newer one goes out too, that is the duplicate above. If it stops before handing over, the row is recorded as sent from the earlier attempt. If its own outcome is unknown, the row is recorded as sent and a `duplicate_send` problem says it may have gone out twice (no event or count: that is not proven) |
| `unknown` after a newer attempt | Recorded as sent, with the same "may have gone out twice" problem |
| `unknown` after this same attempt, `failed`, `cancelled`, `skipped`, queued again or back in review (`draft`, `pending_review`) | Recorded as sent from the late attempt (a queued second try is dropped): nothing else went out, so it is no duplicate. An approval or a resend still asked for about it is cancelled, so approving it never sends it again |

Posts are recorded the same way, with a `duplicate_send` problem about the post (and its `problem.opened` event) and `why.duplicate_attempts`; there is no `message.duplicate` event or campaign count for a post. Repeated visits and likes are not recorded as duplicates.

## Scenarios

| Scenario | What must hold |
| --- | --- |
| S1 | A worker dies mid-send: the next claim finds the row in its handover state and marks it `unknown`; nothing is handed over again |
| S2 | A timeout or dropped connection after handover: `unknown`, no retry |
| S3 | An unclear success (accepted without an id): counted as sent (published for posts), never failed. An answer that is not the provider's own at all, or a 2xx answer to a one-time write whose body broke off before the provider named what it made, is `unknown` |
| S4 | Two workers claim the same row at once: exactly one handover |
| S5 | An error before handover: retried on the same row (no new row, no new message id) |
| S6 | A late success of an older attempt after the row was sent again: recorded as a duplicate, never silent |
| S7 | The caller repeats the same request (an agent retrying after a timeout): one outbound row |
| S8 | An automatic extra attempt: only with proof, at most one, then a person |

## At least once by design

These are done at least once. A repeat is harmless, or the receiver can recognise it.

| What | Why a repeat is fine | What the engine does |
| --- | --- | --- |
| LinkedIn profile visits and likes | Visiting again or liking a post you already liked changes nothing | One found mid-action is done again, up to 3 attempts; one whose call timed out, was cut off or got a server error is tried again like any temporary failure, up to 5 tries of its job. After that, or when the answer cannot be read, it fails, marked as possibly done (`why.failed_before_handover` is false); a campaign step may still try it with a new message an hour later, as for any failed step. A repeat is never recorded as a duplicate |
| Outgoing webhooks | Every delivery carries ids that stay the same on every retry | Failed deliveries retry for about two days. Receivers drop repeats by the body's `id` (the event id, the same for every endpoint and every retry) or the `OpenOutbound-Delivery` header (the same for every retry of one delivery). See [Events](../reference/events.md#webhook-delivery-format) |
| Notifications (Slack, email, webhook channels) | A person can read a message twice | Deliveries run as jobs that retry, so a message whose answer was lost can arrive again |
| CRM sync | Records are keyed by the engine's ids | Contacts, companies and deals are linked to the engine's ids (`crm_links`) and looked up before they are created, so a retry updates the same record. An activity note is written once per event and provider; one whose answer was lost can be written again |
